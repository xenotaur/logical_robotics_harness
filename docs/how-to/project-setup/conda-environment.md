# Setting Up a Conda Environment for LRH Development

## Purpose

Use this guide when you're a new human contributor setting up your own conda environment to work on this repository. It covers the recommended steps, why conda isn't strictly required, and why you won't find a committed `environment.yml` to build from.

If you're setting up an isolated environment for a specific git worktree — for example, running multiple agent sessions against different branches on one machine — use [`scripts/conda-worktree-env`](../../../scripts/README.md#conda-worktree-env) instead. That script solves per-worktree editable-install collisions specifically; this guide is for a single contributor setting up their one development machine.

## Steps

```bash
conda create -n lrh python=3.11
conda activate lrh
scripts/develop
```

`scripts/develop` installs this repository in editable mode from `pyproject.toml`'s `[dev]` extra, constrained by `constraints-dev.txt` — the same source GitHub Actions CI installs from (`.github/workflows/tests.yml`, `.github/workflows/lint.yml`). Using it keeps your local environment matched to CI regardless of whether you got there via conda or venv.

Re-run `scripts/develop` any time `pyproject.toml`'s `[dev]` extra or `constraints-dev.txt` changes.

## Why conda isn't required

This repository's `[dev]` extra (`black`, `build`, `coverage`, `ruff`, `twine`) has no compiled or native dependencies today. A plain venv works identically:

```bash
python -m venv .venv
source .venv/bin/activate
scripts/develop
```

Conda is documented here because it's a common contributor convention, not because this repository needs conda's package management for anything venv/pip can't do. Use whichever you already default to.

## Why there's no `environment.yml`

This repository doesn't commit a conda `environment.yml`. One existed previously, generated by `scripts/update` running a raw `conda env export` against whatever environment happened to be active at the time — not a curated spec, and nothing in CI or `scripts/develop`/`scripts/conda-worktree-env` ever read it for installation. It drifted: its last committed version pinned two different dev-snapshot versions of what is now a single package (`lrh` under its current name, and `logical-robotics-harness` under a prior one), evidence that whoever last ran the export had two coexisting editable installs in their live environment. It was retired along with `scripts/update` rather than fixed, since `pyproject.toml`'s `[dev]` extra plus `constraints-dev.txt` is already the accurate, CI-matching source of truth — see [`scripts/conda-worktree-env`](../../../scripts/conda-worktree-env)'s own rationale for the same conclusion.

If you want an exact snapshot of your own live environment for debugging, `conda env export` still works — just don't commit the result as a setup file.
