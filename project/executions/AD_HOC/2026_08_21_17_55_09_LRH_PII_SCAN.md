Multi-turn `/lrh-design` discussion converged on a design for detecting
PII and misplaced sensitive documents (as distinct from `lrh secrets`'

pre-commit/`.gitleaks.toml` evidence. This session then ran `/lrh-proposal`

# Result

Wrote `project/design/proposals/proposed/lrh-pii-scan/00_proposal.md`
(status `proposed`, `implementation_status: not_started`) covering: a
separate `lrh pii scan` command (not folded into `lrh secrets`); two-layer
detection (file-type/path heuristics first, text-pattern content checks
second, scoped to already-flagged files); full-history coverage via
lightweight git plumbing rather than a bespoke blob-walker;
repo-configurable `.lrh-pii.toml` rules on disclosed defaults, modeled on
LCATS's live `.gitleaks.toml`; shared rule taxonomy (not shared runtime)
with `lrh.conversations.sensitivity`; a lighter `.gitleaksignore`-style
allowlist than `lrh secrets review`'s decisions-file/marker gate; and a
`pii_findings.json` output schema distinct from gitleaks'. Also wrote
`docs/how-to/project-setup/pii.md` stating LRH's PII philosophy (opt-in,
audit-first, precision-scales-with-consequence, structural prevention
preferred, disclosed limitations, human-in-the-loop remediation,
tiered delivery, repo-owned exceptions), and indexed it in
`docs/how-to/project-setup/README.md`. Per explicit direction, the
implementing workstream and work items were deliberately not created in
this PR — that is a separate, later step.
