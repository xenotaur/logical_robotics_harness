# Design new-contributor conda environment setup and resolve environment.yml drift

## Summary

Decide and document how a new human contributor (not an agent worktree)
sets up their own working conda environment for this repo, and resolve
`environment.yml`'s current drift as part of that decision.

## Problem / Context

`environment.yml` is a raw `conda env export` snapshot regenerated by
`scripts/update` (`scripts/update:3`) -- it captures whatever's live in
*whoever's* currently-active conda env at the moment they run it, not a
curated spec. Its `pip:` section currently pins two separate entries for
what is now one package: `logical-robotics-harness==0.2.5.dev41+...` and
`lrh==0.2.5.dev83+...`. `pyproject.toml:6` names the package `lrh`;
`logical-robotics-harness` is a stale prior name. The two different
dev-snapshot pins are themselves evidence that whoever last ran
`scripts/update` had both an old and a new editable install coexisting in
their live env -- i.e. this file is a fossil of someone else hitting the
same multi-worktree editable-install collision that
`scripts/conda-worktree-env` (PR #600, merged) now fixes for concurrent
agent worktrees.

Nothing in CI or the current documented setup path
(`scripts/develop`/`scripts/conda-worktree-env`) reads `environment.yml`
for installation, so this is currently cosmetic/inert -- but it's a real
trap for anyone who tries to bootstrap from it, and README.md's
"Environment notes" section (`README.md:328`) is currently thin on what a
human contributor should actually do.

### Duplication search

- In-repo: `PROP-DEV-TOOLCHAIN-ENV-RESOLUTION` (adopted 2026-07-14,
  `project/design/proposals/adopted/dev-toolchain-env-resolution.md`)
  already frames and decides the adjacent question of environment
  *resolution* (which interpreter/env canonical scripts run in), adopting
  Option C: LRH-native version guardrails are mandatory everywhere;
  Taurworks activation (`.taurworks/config.toml [activation.environment]`
  + `tw activate`) is an optional, detected resolver, never a hard
  dependency -- chosen specifically to avoid a circular LRH<->Taurworks
  dependency. That proposal explicitly deferred filing a work item for
  "the optional-Taurworks detection/interface contract" until Taurworks'
  own producer-side work (`WI-ACTIVATION-PRODUCERS-0001`) stabilizes, and
  its own Non-Goals exclude "non-conda environment strategies
  (venv/Docker)." Not a clean duplicate of new-contributor conda setup
  specifically, but the governing architectural decision this work must
  fit inside, not route around.
- Sibling repos: `taurworks` owns the Taurworks-side producer work
  referenced above; not duplicated here.
- External libraries: None identified.
- Recommendation: Proceed, but explicitly reconcile with
  `PROP-DEV-TOOLCHAIN-ENV-RESOLUTION`'s adopted Option C rather than
  re-deciding it, and do not implement the deferred Taurworks-contract
  work as part of this item.

## Scope

- Investigate and design (via `/lrh-design`) how a new human contributor
  should set up a working conda environment for this repo.
- Decide `environment.yml`'s fate: regenerate cleanly, or retire it.
- Document the chosen setup path.

## Required Changes

1. Run `/lrh-design` (or produce an equivalent design artifact) covering:
   whether to regenerate `environment.yml` from a known-clean env or
   retire it; where to document contributor conda setup (README.md vs. a
   new `docs/how-to/project-setup/` playbook, or both); whether conda is
   worth keeping as the recommended path over a plain venv for new
   contributors, given this repo has zero compiled/native pip
   dependencies today.
2. Implement the documentation decided in (1).
3. If `environment.yml` is kept, regenerate it cleanly from a verified
   env with no stale `logical-robotics-harness` remnant.
4. If `environment.yml` is retired, remove it and `scripts/update`
   together, and update any doc that references either.

## Non-Goals

- Does not touch `scripts/conda-worktree-env` itself -- that's a
  separate, already-solved problem for concurrent agent worktree
  isolation.
- Does not implement the Taurworks detection/interface contract deferred
  by `PROP-DEV-TOOLCHAIN-ENV-RESOLUTION` -- that is explicitly that
  proposal's own follow-on, spun only once Taurworks' producer side
  stabilizes.
- Does not decide non-conda environment strategies (venv/Docker) as a
  general policy -- `PROP-DEV-TOOLCHAIN-ENV-RESOLUTION` already scoped
  that out; this item may note venv as an alternative for this specific
  contributor-onboarding case without re-opening the general question.

## Risk Notes

- **Scope-creep risk toward the deferred Taurworks contract.** The
  environment-resolution design space is shared territory with
  `PROP-DEV-TOOLCHAIN-ENV-RESOLUTION`; a design session here could drift
  into re-deciding or implementing that proposal's own deferred
  follow-on. The Non-Goals and `forbidden_actions` above exist
  specifically to bound this.
- **`environment.yml` regeneration risk.** If kept, regenerating it from
  a not-actually-clean env would just recreate the same drift under new
  version numbers -- must verify the source env has no stale
  `logical-robotics-harness` remnant first (e.g. via
  `scripts/conda-worktree-env <name> --recreate`).
